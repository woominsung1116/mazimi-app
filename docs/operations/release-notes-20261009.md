운영자와 QA를 위한 배포 메모다. 이번 릴리스는 DB 마이그레이션, 세션 방식, 신청 준비 체크 목록, 공개 API 동작, 신청처 검토 규칙을 바꾼다. 배포 전에 아래 항목을 순서대로 확인한다.

- `20261008*` 번호는 첫 운영 배포 전에 번호를 다시 매기고 내용을 고쳤다. 이전 버전을 적용한 스테이징·개발 DB는 마이그레이션 체크섬이 맞지 않아 기동에 실패한다. 그런 DB는 고치지 말고 새로 만든 뒤 처음부터 마이그레이션한다.
- 운영 DB에는 이 번호들이 아직 적용돼 있으면 안 된다. 배포 전에 `_sqlx_migrations`에 `20261008%`나 `20261009%` 버전이 없는지 확인한다.
- 000002와 000004의 백업 테이블(`benefit_source_candidate_review_backup`, `user_profile_status_backup`)은 되돌리기 전용이다. 배포 후 30일 이상 안정적이면 후속 마이그레이션으로 삭제한다. 되돌리는 SQL은 각 파일 머리말에 있다.
- 000006은 `encrypted_answers`만 비운다. `application_submissions`의 다른 열과 `queued` 행은 남는다. 보유 근거와 정리 방법은 아직 결정하지 않았다(아래 7절).

## 2. 세션: 일회성 재로그인과 refresh 회전

- 000003부터 refresh token을 서버에서 추적하고, 쓸 때마다 회전한다. 이전 방식으로 발급된 refresh token은 서버 기록이 없어 갱신되지 않는다. 그래서 배포 후 기존 사용자는 액세스 토큰이 만료되면 한 번 다시 로그인해야 한다. 고객 문의 응대 문구에 반영한다.
- 회전된 토큰이 60초 안에 다시 오면 다음처럼 처리한다.
  - 후속 토큰이 아직 쓰이지 않았으면 응답 유실로 보고 체인을 이어 준다.
  - 후속 토큰이 이미 쓰였으면 401을 돌려주고, 그 토큰에서 시작한 회전 체인을 폐기한다. 다른 기기의 세션은 그대로 둔다.
  - 60초가 지난 뒤 다시 오면 탈취로 보고 그 계정의 refresh token을 모두 폐기한다.

## 3. 신청 준비 체크 목록 초기화 (revision v7)

- 체크 목록 revision 버전이 7로 올라갔다. 이제 revision은 신청처의 정체성만 반영한다. 정체성은 공개된 적 있는 자료의 id·주소·접근 방식, 양식 파일 해시, 안내 목적지 주소다.
- 검증 만료, 같은 신청처 재승인, 문구 변경으로는 체크가 초기화되지 않는다. 다른 주소 승인, 접근 방식 변경, 강등·거절, 새 모집 회차는 한 번 초기화한다.
- 배포 직후에는 저장된 revision(v6 이하)과 값이 달라서, 사용자가 공고를 처음 열 때 체크 진행 상태가 한 번 초기화되고 안내가 표시된다. 오류가 아니다.

## 4. API 동작 변경

- `GET /api/v1/programs`: `status` 파라미터가 없으면 지금 신청 가능한 공고만 돌려준다. 예정 공고와 마감 공고는 `status=upcoming`, `status=closed`로 따로 요청한다.
- `POST /api/v1/stack-check`: 사용 중단(deprecated)이다. 응답에 `Deprecation`과 `Sunset: Sun, 31 Jan 2027 00:00:00 GMT` 헤더가 붙는다. 새 클라이언트는 호출하지 않는다.
- 혜택 도우미 질문:
  - 사용자별로 분당 10회를 넘으면 429를 돌려준다.
  - 질문을 보내기 전에 보이지 않는 서식 문자, 전각 숫자, 구분자 3자까지 끼운 6자리 이상 숫자열, `www.` 링크를 가린다. 다만 완전한 탐지는 아니며, 개인정보처리방침에도 그렇게 적었다.
- `POST /api/v1/assistant/compare`: 금융상품이 하나라도 포함되면 400을 돌려준다. 금융상품은 `program_type`이 금융 유형이거나, `source_type = fss_financial`이거나, `benefit_category = finance`인 공고다. 묶음(`bundles`)에서도 같은 기준으로 제외한다.
- 분류기의 범위 밖 차단은 요청형 표현에만 적용된다. 예를 들어 "저장해 둔 혜택 마감 언제야?", "다른 사람도 신청할 수 있어?"는 더 이상 막지 않는다. holdout 정확도 기준선은 55/61 = 90.2%다. 이전 보고(68/74)는 분류기 튜닝에 쓴 리뷰 예시 13개가 섞인 값이다. AI flag를 켜려면 93.2% 이상이 필요하다(`docs/mazimi-ai-assistant-v1-contract.md`).

## 5. 추천 노출 변화

학적 조건(`normalized_payload.enrollment_statuses`)을 이제 공고 유형과 상관없이 적용한다. 비캠퍼스 공고 중 이 값을 가진 것은 `20260923000015_expand_student_benefits.sql`이 넣은 기업 학생 할인 18건뿐이다(`["enrolled","재학"]`).

- 저장된 학적이 `on_leave`, `graduated`, `research_student`인 사용자에게는 `/recommend/preview`와 묶음의 "일상 소비 혜택"에서 이 18건(Apple, Adobe, GitHub Pack 등)이 빠진다.
- 학적을 입력하지 않은 사용자에게는 이전처럼 보인다.
- 의도된 일관성 변경이다. 휴학생도 받을 수 있는 혜택인지는 데이터에서 따로 확인한다.

## 6. 신청처(신청 자료) 검토와 수집기

- 워커 기능 플래그: 신청 자료 확인 작업은 `APPLICATION_RESOURCES_ENABLED`가 `true` 또는 `1`일 때만 실행되고, 기본값은 꺼짐이다. 운영에서 켜기 전에 출처 접근 정책 검토를 먼저 마친다.
- 도메인 바인딩: 신청처는 수집된 공고 공식 주소와 같은 기관 도메인이어야 `verified`로 승인할 수 있다. 다음 경우는 그 호스트를 승인 출처 도메인(`benefit_source_domains`)으로 먼저 등록해야 한다.
  - 관리자가 입력하거나 고친 `official_url`(이 값은 `admin_official_url`로 기록되고 경고 로그를 남긴다)
  - 공유 호스팅(`core::source_policy::SHARED_HOSTING_*`)
  - IDN(`xn--`) 주소

  공유 호스팅은 두 종류다. naver.com·google.com 같은 경로 테넌트는 공식 주소의 기준이 되지 않는다. github.io·tistory.com 같은 서브도메인 테넌트는 정확히 같은 호스트만 같은 기관으로 인정한다.
- 로그인 게이트: `login_required` 신청처의 리디렉션은 같은 등록 도메인(공유 호스팅 제외) 안의 로그인 경로 세그먼트로 갈 때만 정상이다. 외부 SSO를 포함해 다른 사이트로 가는 리디렉션은 실패로 기록하고, 승인된 행이면 운영 이벤트 `application_resource_redirected`를 남긴다. 리디렉션만으로는 강등하지 않는다.
- robots.txt는 실행마다 (승인 스코프, 호스트) 단위로 읽는다. 서브도메인을 허용하는 스코프에서는 호스트 수만큼 robots 요청이 늘어난다.
- 승인하면 이전 수집 오류(`check_error`, `last_failure_code`)도 함께 지운다. 마감되거나 예정인 공고에는 "다시 확인 중"을 표시하지 않는다.
- 공식 주소 저장 방식: 관리자 `official_url`과 공고 원문의 `official_links`는 앞뒤 공백만 지운 원문 그대로 저장한다. 검증과 중복 판정에만 정규형을 쓴다. 그래서 SPA fragment(`#/apply/12`)와 EUC-KR 쿼리가 보존된다.
- 신청 자료 fingerprint가 v2로 바뀌었고 백필은 없다. 운영 DB에는 아직 신청 자료 데이터가 없으므로 영향이 없다. 운영 데이터가 생긴 뒤 fingerprint를 다시 바꿀 때는 백필 SQL이나 이벤트 억제가 필요하다. 그러지 않으면 기존 verified 행이 모두 비공개로 바뀌고 `application_resource_changed` 이벤트가 행마다 쌓인다.

## 7. 알려진 남은 일

- 로그아웃할 때 액세스 토큰이 이미 만료됐으면 푸시 토큰이 서버에 남는다(보안 L2). `/auth/logout`에서 푸시 토큰도 정리하도록 바꿀 예정이다.
- 기관 연결 신청 기능의 과거 기록(`application_submissions`)을 얼마나 보유할지, 처리방침에 어떻게 고지할지 정해야 한다(보안 L8).
- 사용자별 질문 한도는 프로세스 메모리에 있다. API 인스턴스를 늘리기 전에 공유 저장소로 옮긴다.
